# ISMERS FAM Seeding

These files seed fictional development and capstone demonstration data for the existing MySQL 8.0+ database `ismers_fam`.

## Required Database

Use the imported `ismers_fam` schema.

## Import Order

1. Import the schema, for example `ismers_fam_aligned_schema_mysql8.sql`.
2. Import `database/seed_reference_data.sql`.
3. Import `database/seed_demo_transactions.sql`.

Both seed files are wrapped in `START TRANSACTION;` and `COMMIT;` and are intended to run safely in phpMyAdmin.

## Rerun Safely

`seed_reference_data.sql` uses stable codes and `INSERT ... ON DUPLICATE KEY UPDATE` for reference data.

`seed_demo_transactions.sql` removes only records with known demo prefixes before reinserting:

- `FR-2026-%`
- `WO-2026-%`
- `RR-2026-%`
- `PR-2026-%`
- `DOC-2026-%`

Do not run broad deletes against reference tables unless you intentionally want to reset master data.

## Final Role Model

Fresh development/bootstrap data now uses only these canonical application roles:

- `FAM_SUPER_ADMIN` = FAM system super administrator
- `FAM_ADMIN` = FAM Department Head
- `FAM_STAFF` = ordinary FAM operational employee
- `DEPARTMENT_HEAD` = head of a non-FAM department
- `EMPLOYEE` = ordinary employee

Organizational position and application authorization are separate concepts. A FAM Department Head belongs to the FAM department and has `FAM_ADMIN`; do not also assign `DEPARTMENT_HEAD`. A non-FAM department head is identified by `department_reference.department_head_employee_reference_id` and has `DEPARTMENT_HEAD`.

## Fixed Demo Date

The transaction seed uses the fixed demo date `2026-07-26 10:00:00` so screenshots, reports, dashboard badges, due dates, and calendar views remain stable.

## Removing Demo Transactions Only

To remove only demo transactional data while preserving reference data, rerun the cleanup section at the top of `seed_demo_transactions.sql` or rerun the whole file. The cleanup targets only stable demo prefixes and known deterministic demo rows.

## Fictional Data Notice

All names, departments, suppliers, contact details, paths, IDs, budgets, contracts, and activity data are fictional and intended only for development, UI testing, API testing, and capstone demonstration.

## Schema Limitations

The current schema does not include these requested tables:

- `facility_amenity` or a facility space amenity junction table
- `asset_document`
- `maintenance_activity`
- `contract_document`
- `contract_milestone`
- `contract_history`
- `record_disposition`
- `integration_log`

The seed files do not invent these tables. Where possible, equivalent demo coverage is represented through existing tables such as `document`, `document_version`, `record_document`, `maintenance_history`, `activity_event`, `audit_log`, `notification`, and `integration_outbox`.
